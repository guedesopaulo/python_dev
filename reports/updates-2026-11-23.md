### The three criticals, in detail

- **`certifi` 2026.7.22** — [GHSA-6q48-6c7w-9gw2](https://github.com/advisories/GHSA-6q48-6c7w-9gw2), CWE-295. Bundles the `emSign ECC Root CA - G3` root, under which 8 eMudhra intermediate CAs had their private keys compromised and revoked. An attacker holding one of those keys can mint certificates for any hostname; on-path, they could intercept TLS traffic from anything trusting this bundle (`requests`, `urllib3`, `pip`, …). Fixed in 2026.10.19 (2026.10.18 pulled the roots entirely; .19 restored the unaffected ones). The advisory explicitly warns that bumping `certifi` alone doesn't help already-built container images that vendored the old bundle — rebuild, don't just relock.
- **`authlib` 1.8.0** — [GHSA-6v38-4h7w-rj9h](https://github.com/advisories/GHSA-6v38-4h7w-rj9h), CVSS 9.1, CWE-347. `JsonWebSignature.deserialize_json()` initializes `is_valid = True` before checking anything, then only ever flips it to `False` inside the per-signature loop — so a JWS JSON object with an **empty** `signatures` array skips the loop entirely and returns the payload as "verified" with no signature and no key. Fixed in 1.9.0.
- **`pyjwt` 2.13.0** — [GHSA-ffc3-869f-jxw9](https://github.com/advisories/GHSA-ffc3-869f-jxw9), CVSS 9.1, CWE-347. The guard against mixing an HMAC and an asymmetric algorithm in the same `algorithms=[...]` allow-list (the classic RFC 8725 "alg confusion" footgun) relies on a regex, `is_pem_format`, to detect a PEM key. A key with marker-adjacent whitespace, CR-only line endings, or folded onto one line — all forms `cryptography`'s own loader accepts — slips past the regex, re-opening the confusion attack the guard exists to close. Fixed in 2.14.0.

### What `uv lock --upgrade` doesn't fix

One `pyjwt` alert, [GHSA-gvp8-978c-rx2q](https://github.com/advisories/GHSA-gvp8-978c-rx2q) (CVSS 6.5, CWE-471), has **no patched version at all**: `PyJWT.decode()`/`decode_complete()` mutates a caller-supplied `options` dict in place when `verify_signature` is falsy, so reusing that same dict across calls can silently disable claim checks on a later, supposedly-strict call. Not applicable here regardless — this app never calls `pyjwt.decode()`.

Two `fastmcp`/`fastmcp-slim` moderate alerts are worth a closer read since `src/main.py` does use `FastMCP.from_fastapi()`: [GHSA-7xgj-8392-5q4r](https://github.com/advisories/GHSA-7xgj-8392-5q4r) (CVSS 6.8) — a server-transform could let a client fetch a component the configured authorization policy denies, by calling it directly instead of through the transform; and [GHSA-vqqp-x5qm-5qp4](https://github.com/advisories/GHSA-vqqp-x5qm-5qp4) (CVSS 5.9) — FastMCP's OAuth client-credentials wrappers didn't bind to a specific authorization-server issuer. Neither applies: this repo configures no authorization policy, no server transforms, and no OAuth client-credentials provider. Both are fixed in 4.1.2 regardless.

**Bottom line:** every one of the 64 open alerts traces back to how far behind `fastmcp` (runtime) and `pre-commit` (dev) are, not to anything this app's own code does — but they're real, GitHub-confirmed, and a single `uv lock --upgrade` (or at minimum, targeted bumps of `fastmcp`, `authlib`, `pyjwt`, `certifi`, `dnspython`, `pre-commit`) closes all but the one unfixable, inapplicable `pyjwt` design-limitation alert.

## New community practices

- **Pin GitHub Actions to a commit SHA, not just a full version tag (verified).** This repo already avoids floating major tags ("astral-sh no longer publishes the moving @v8 major tag" comment in `ci.yml`), but a full version tag (e.g. `@v0.36.0`) is still a mutable ref an attacker with repo/token access can repoint — which is exactly what happened to `aquasecurity/trivy-action` in March 2026 ([GHSA-69fq-xp46-6x23](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23): most tags 0.0.1–0.34.2 force-pushed to a credential-stealing commit). `astral-sh/setup-uv`'s own README now documents SHA-pinning as the default example (`astral-sh/setup-uv@<sha> # v10.4.0`). This repo's tag pin (`v0.36.0`) postdates and is unaffected by that specific incident, but the next tag it adopts carries the same category of risk.
- **FastAPI now ships native request-size and concurrency controls (verified, [0.163.0–0.165.0 release notes](https://github.com/fastapi/fastapi/blob/master/docs/en/docs/release-notes.md)).** `Depends(max_concurrency=...)` caps concurrent calls into a dependency, and `FastAPI(...)` / route-level options can now cap request body and form-parsing size. Not yet actionable here — the only endpoint (`/echo`) is a bare `Query` parameter with no body — but worth knowing before the next endpoint that accepts a body or file upload is added, as an alternative/complement to the hand-rolled per-IP `rate_limit()` dependency in `src/dependencies.py` (which is about request *rate*, not payload *size* or *concurrency*, so the two are complementary, not a replacement).
- **uv 0.13.0 makes Python 3.15 the default stable download (verified, [uv CHANGELOG](https://raw.githubusercontent.com/astral-sh/uv/main/CHANGELOG.md)).** Not actionable here: the Dockerfile sets `UV_PYTHON_DOWNLOADS=0` and pins `python:3.13-slim-bookworm` explicitly, and `pyproject.toml` requires `>=3.13`, so nothing in this repo relies on uv's "no version requested" fallback.
- **FastMCP 4.2 adds a Skills extension and an Events/subscriptions extension (verified, [FastMCP updates](https://github.com/PrefectHQ/fastmcp/releases)).** Flagged for awareness only, not as a recommendation — reference.md's standing decisions explicitly keep this repo's scope minimal ("no docs site, no Python version matrix... deliberate scope limits for a minimal starter"), and adopting either extension would be exactly that kind of scope growth.

## Recommendations

1. **Run `uv lock --upgrade` and merge it — this is the week's priority, not a nice-to-have.** It closes all 64 open Dependabot alerts (3 critical, 22 high, 34 moderate, 5 low) in one shot, verified directly in this research (ran it, checked every fixed-version floor, reverted). No code change is required — every affected package is transitive — and no breaking change surfaced anywhere in the diff touches this repo's actual usage. The one `pyjwt` alert with no fix available ([GHSA-gvp8-978c-rx2q](https://github.com/advisories/GHSA-gvp8-978c-rx2q)) doesn't apply regardless, since nothing here calls `pyjwt.decode()`.
2. **Re-run `make audit` once `api.osv.dev` is reachable from this environment**, or rely on CI/Dependabot in the meantime — both already see this repo. This report's Dependabot cross-check is a reasonable stand-in for one week, not a permanent substitute: Dependabot's alert feed and `uv audit`'s osv.dev feed don't always have identical coverage or timing.
3. **Bump `ruff` (dev dep) and `astral-sh/ruff-pre-commit` together**, and **`mypy` (dev dep, exact pin) and `pre-commit/mirrors-mypy` together** — both are standing lock-step policies already, just behind by one minor version each. Low risk; `make check` is the verification gate.
4. **Bump the `uv` pin in all three places together** (Dockerfile, `.pre-commit-config.yaml`, `ci.yml`) from 0.12.10 to 0.13.9, and let `astral-sh/uv-pre-commit`'s rev follow it, same as today's internal-consistency pattern. None of 0.13.0's breaking changes apply to this repo's usage (reviewed above).
5. **Bump `actions/checkout` to v7.0.1 and `astral-sh/setup-uv` to v10.4.0.** Both majors were read end-to-end; neither changes this repo's actual CI behavior (no `pull_request_target`/`workflow_run` triggers), though `setup-uv`'s new `prune-cache: false` default is worth a one-line mental note for future Actions cache usage.
6. **Consider SHA-pinning GitHub Actions** (keeping the version as a trailing comment, as `setup-uv`'s own README now recommends) as a follow-up hardening pass — evidenced by the real `trivy-action` incident above, not speculative.
7. **No Dockerfile or `trivy-action`/`hadolint-action`/`shellcheck-py` changes needed** — all three are already at the latest verified tag.
