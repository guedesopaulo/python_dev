## New community practices

- **FastMCP tightened Streamable HTTP transport security** (Host/Origin validation, SSRF-hardened OAuth
  metadata/JWKS fetches with a trusted-proxy allowlist) across 3.4.1–3.4.6. Relevant because this repo
  mounts `mcp_app` directly on the same ASGI app with no origin/host validation beyond the global
  bearer-token check — worth reviewing when `fastmcp` is next bumped. Source:
  [FastMCP changelog](https://gofastmcp.com/v3/changelog.md) (verified, via official changelog text).
- **FastMCP's own auth docs** describe `TokenVerifier`/`JWTVerifier` (JWKS-based, issuer/audience
  checked) as the framework-native way to authenticate MCP calls, as an alternative to a blanket
  ASGI bearer check. This repo deliberately uses the latter (`BearerTokenMiddleware` covers `/mcp` too,
  per CLAUDE.md) — noting this as an option for when cloud-environment JWT/OAuth2 validation is filled
  in, not a problem today. Source: [FastMCP token verification docs](https://gofastmcp.com/v3/servers/auth/token-verification.md)
  (unverified — page content read via search snippet, direct fetch to the domain failed in this
  session).
- **The MCP spec's 2025 updates deprecated HTTP+SSE for new servers in favor of Streamable HTTP**,
  which this repo already uses (`mcp.http_app(transport="http", ...)`) — confirms the current choice
  needs no change. Source: third-party 2026 MCP security guide (unverified).
- **`uv` now rejects/fixes non-canonically-formatted lockfiles** under `--locked`/`--check`
  (`uv lock --check`) as of `v0.11.32`, and stopped pulling in workspace-root default dependency groups
  for a single synced member as of `v0.12.2`. Neither changes this repo's behavior (single-project,
  `uv sync --locked` in CI, `dev` is the only group), but is good to know before the pending `uv` bump
  above. Source: uv changelog entries via a GitLab Renovate mirror (unverified — not the primary
  `astral-sh/uv` changelog, which this session could not reach for a page-by-page read).
- **No new split between `uv run` and `uvx` guidance** beyond what this repo already follows: project
  code runs via `uv run` (locked dependencies), standalone tools via `uvx`/`uv tool run` (isolated,
  unpinned) — confirms the Makefile's existing "never `uvx`" convention is still the documented
  recommendation precisely because it avoids the unpinned-tool problem. Source:
  [uv docs mirror on `uv run` vs `uvx`](https://pydevtools.com/handbook/explanation/when-to-use-uv-run-vs-uvx/)
  (unverified — third-party handbook, not astral-sh's own docs).

## Recommendations

1. **Re-run `uv audit` in an environment that can reach `api.osv.dev`** before trusting any dependency
   as vulnerability-free this week — this run's audit did not execute, it didn't pass. (Security; top
   priority because every other finding here is built on top of an unknown CVE baseline.)
2. **Bump `uv` from `0.12.10` to `0.13.5` in all three pinned locations together** (pre-commit, CI,
   Dockerfile) — keeps the existing "uv pinned in lock-step" convention intact; nothing in this repo
   depends on a uv behavior that changed in between.
3. **Bump `ruff` (dev dependency) and the `ruff-pre-commit` rev together**, `0.16.6` → `0.17.2` —
   mirrors the lock-step pattern this repo already enforces for `mypy`/`mirrors-mypy`, and avoids the
   hook and the dependency silently disagreeing.
4. **Consider bumping `mypy==2.3.1` → `2.4.0` together with the `mirrors-mypy` rev** (`v2.3.1` →
   `v2.4.0`, both confirmed to exist) — low risk, same lock-step requirement.
5. **Bump the direct web-stack dependencies** (`fastapi`, `fastmcp`, `starlette`, `uvicorn`,
   `pydantic-settings`) as a batch, then run the full verification ritual (`uv sync --locked` →
   `make check` → `make cov` → `make smoke`) — no blocking breaking change was found for this repo's
   current code, but `fastmcp`'s session-timeout and trust-store changes are worth a manual look at the
   `mcp-standalone` smoke test afterward.
6. **Review `actions/checkout` (v6→v7) and `astral-sh/setup-uv` (v8.2.0→v10.3.2) release notes before
   bumping** — both are major-version jumps on Actions whose own versioning doesn't track `uv`'s;
   `checkout` v7's fork-PR restriction doesn't affect this repo's triggers, but should be confirmed
   rather than assumed.
7. **Low-priority cleanup**: once `starlette` is past `1.6.0`, check whether the `filterwarnings`
   ignore for `anyio.abc.BlockingPortal` in `pyproject.toml` is still needed — the 1.7.0 release notes
   suggest the underlying `TestClient` behavior it works around was fixed upstream.
8. **No action**: the Dockerfile's `python:3.13-slim-bookworm` base image tag floats and already tracks
   the newest 3.13.x patch automatically; nothing to pin or bump here.
