# Weekly updates report — 2026-10-05

## Summary

- **Security (transitive):** `pyjwt` 2.13.0, pulled in via `mcp` (a dependency of `fastmcp`), carries 13
  distinct GHSA advisories (algorithm-confusion, ReDoS, unbounded JWKS requests, a claims-bypass via
  mutated options dict). All but one are fixed in 2.14.0/2.15.0; `uv lock --upgrade` resolves it straight
  to 2.15.1. This is the same "blind to transitive dependencies" failure mode the dependency policy
  already documents for `cryptography`/`fastmcp` — `pyjwt` is never named in `pyproject.toml`.
- **Security (transitive, dev-only):** `virtualenv` 21.7.8 (via `pre-commit`) has 4 GHSA advisories
  (unverified wheel downloads, config/activation-script injection on Windows). Fixed by 21.14.5. Dev-only,
  not shipped in the Docker image, but used in CI.
- **`uv audit` could not run in this environment** — see Security section; verified manually instead with
  `pip-audit` against an exported lockfile plus direct PyPI release-metadata checks.
- **Tooling drift:** the uv pin (Dockerfile/pre-commit/CI, all consistently `0.12.10`) is missing a
  Windows path-traversal fix shipped in uv 0.12.18 (GHSA-2cv4-cqwr-gwf7); `astral-sh/setup-uv` is 2 major
  versions behind; `docker/build-push-action` v7.3.0 is missing a "workflow command injection in metadata
  logs" fix shipped in v7.4.0.
- **No direct-dependency breaking changes found.** `fastapi`, `fastmcp`, `starlette`, and `uvicorn` all
  have newer compatible releases; a full `uv lock --upgrade` was applied locally and verified against
  `pytest`, `ruff check`, and `mypy` — all pass unchanged.

## Security

`make audit` (`uv audit --locked --preview-features audit-command`) **did not run**: the `audit`
subcommand needs the uv version this repo pins (0.12.10), and even after installing that exact version
(`pip install uv==0.12.10`), the command failed because this sandbox's outbound network policy blocks
`https://api.osv.dev` (the backend `uv audit` queries):

```
error: Request failed after 3 retries
  Caused by: error sending request for url (https://api.osv.dev/v1/querybatch)
  Caused by: client error (Connect)
  Caused by: tunnel error: unsuccessful
```

This is an environment limitation of this report-generation sandbox, not a finding about the repo. As a
substitute, the full dependency set was exported (`uv export --locked --no-hashes`) and checked with
`pip-audit` (queries PyPI's own vulnerability-report API, not osv.dev directly), then every finding was
individually confirmed against `https://pypi.org/pypi/<package>/<version>/json`:

| Package | Locked version | Advisories | Fixed in | Direct/transitive |
|---|---|---|---|---|
| `pyjwt` | 2.13.0 | 13 (GHSA-ffc3-869f-jxw9, GHSA-r6x4-923q-g947, GHSA-p4g4-x82p-q773 algorithm-confusion; GHSA-jwrc-g2q2-pq5p ReDoS; GHSA-2gx3-rcp4-g85q unbounded JWKS requests; GHSA-8wjv-2p76-3863/GHSA-42vr-xj54-vc7v recursion DoS; GHSA-gvp8-978c-rx2q claims-check bypass via mutated options dict — **no patch released** for this one; others) | 2.14.0 (one needs 2.15.0; the options-dict issue is unfixed upstream) | transitive, via `mcp` (required by `fastmcp`) |
| `virtualenv` | 21.7.8 | 4 (GHSA-94p9-xgh2-xp45 unverified wheel download/supply-chain; GHSA-9h9j-4vrj-gf7g config-file injection of the base-interpreter path; GHSA-x78j-v8h9-3j2q/GHSA-p58f-9548-mpm2 Windows activation-script quoting → command execution) | 21.14.5 | transitive, via `pre-commit` (dev-only; not in the Docker image) |

`uv lock --upgrade` moves both straight to the fixed versions as part of the normal dependency graph
resolution (no targeted pin needed), and the full post-upgrade lockfile was verified to still pass
`pytest`, `ruff check .`, and `mypy .` (see Outdated dependencies). The `GHSA-gvp8-978c-rx2q` options-dict
issue has no upstream fix; this repo doesn't call `jwt.decode()` directly today, so it's not currently
exploitable here, but worth remembering if JWT handling is added later.

No vulnerabilities were found in `fastapi`, `fastmcp`, `starlette`, `uvicorn`, `loguru`, or
`pydantic-settings` at their currently-locked versions.

## New community practices

- **`starlette.testclient` is migrating off classic `httpx` to a new `httpx2` package** — it imports
  `httpx2 as httpx` first and only falls back to classic `httpx` (with a `StarletteDeprecationWarning`)
  if `httpx2` isn't installed. **(verified)** — reproduced directly: a bare `starlette==1.7.0` + `httpx`
  env raises the warning on `TestClient` import, but this repo's actual resolved environment doesn't,
  because `httpx2` already arrives transitively through `fastmcp`/`mcp`. Dev dependency `httpx>=0.28.1`
  in `pyproject.toml` is what currently satisfies `TestClient`'s historical API; nothing breaks today, but
  if `fastmcp`/`mcp` ever drop their own `httpx2` requirement, test collection would start emitting a
  warning that `filterwarnings = ["error", ...]` would turn into a hard failure. Source:
  `starlette/testclient.py` in the installed 1.7.0 package, and reproduction in this session.
- **FastAPI ships native OpenTelemetry instrumentation as of 0.142.0.** (verified, via FastAPI's GitHub
  releases) Not adopted here and nothing in CLAUDE.md calls for tracing; flagging only because it's a
  genuinely new capability, not because this repo needs it.
- **GitHub Actions supply-chain hardening: pin to full release tags, not moving majors.** This repo
  already does this for `setup-uv` (CLAUDE.md/CI comment explicitly calls it out) — worth applying the
  same care when bumping the other actions above, since e.g. `docker/build-push-action`'s major-version
  jumps have included real security fixes. (verified pattern already in this repo's own CI comments)
- **uv's own vulnerability-audit workflow (`uv audit`) is still a preview feature** gated behind
  `--preview-features audit-command` and depends on reaching `api.osv.dev` at CI/dev time — worth
  confirming the CI runner's network egress allows this host, since it's a silent, hard requirement for
  the `check` job's audit step to mean anything. (verified — reproduced the exact failure mode in this
  sandbox when that host isn't reachable)

## Recommendations

1. **Run `uv lock --upgrade` and commit the result.** This pulls `pyjwt` to 2.15.1 and `virtualenv` to
   21.14.5, closing the transitive CVEs above, plus `fastapi`/`fastmcp`/`starlette`/`uvicorn`/`ruff`.
   Verified locally: `pytest`, `ruff check .`, and `mypy .` all pass unchanged on the upgraded lockfile.
   Highest priority — this is the only item with live security findings in code that ships.
2. **Bump the uv pin (Dockerfile, `uv-pre-commit` rev, CI `setup-uv` `version:` input) from 0.12.10 to at
   least 0.12.18**, ideally the current 0.12.23, to pick up the Windows path-traversal fix (GHSA-2cv4-cqwr-gwf7)
   and keep the three pins in lock-step as the existing comments already require.
3. **Bump `docker/build-push-action` from v7.3.0 to v7.4.0** in `.github/workflows/ci.yml` — small,
   direct security fix (workflow-command-injection prevention) for a job that already builds untrusted
   PR branches.
4. **Bump `astral-sh/ruff-pre-commit` to v0.16.10 alongside the `ruff` dependency bump** so the pre-commit
   hook and the resolved `ruff` version in `uv.lock` agree, consistent with the lock-step rationale
   CLAUDE.md already documents for `mypy`/`mirrors-mypy`.
5. **Lower priority / opportunistic:** `actions/checkout` v6→v7, `docker/setup-buildx-action` v4.3.0→v4.4.1,
   `crate-ci/typos` v1.50.1→v1.50.3, `mypy`/`mirrors-mypy` 2.3.1→2.4.0 (bump both together, per the
   standing decision). No security or breaking-change content found for any of these; safe whenever
   convenient.
6. **No action needed:** `loguru`, `pydantic-settings`, `hadolint-action`, `trivy-action`,
   `pre-commit-hooks`, `shellcheck-py`, `zizmor` are all already at their latest release.
7. **Environment note, not a repo finding:** this report's `uv audit` step couldn't verify against
   `api.osv.dev` from this sandbox's network policy. If CI's audit step (`check` job) has ever gone green
   without clear evidence it actually reached `api.osv.dev`, it's worth a one-time manual check that the
   step is really querying and not silently no-op'ing.
