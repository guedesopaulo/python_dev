# Weekly Updates Report — 2026-11-02

## Summary

- **Critical transitive CVE in the lockfile today:** `authlib` is locked at `1.8.0`, which carries **CVE-2026-96760** (CVSS 9.1, [GHSA-6v38-4h7w-rj9h](https://github.com/advisories/GHSA-6v38-4h7w-rj9h), signature-verification bypass), fixed in `1.9.0`. It is pulled in transitively by `fastmcp` and isn't named in `pyproject.toml`, so a targeted `uv lock --upgrade-package` would miss it — this is exactly the blind spot `reference.md` calls out for transitives. **Top-priority fix: run `uv lock --upgrade` (or at minimum `uv lock --upgrade-package authlib`) to pull in `>=1.9.0`.**

## Security

- **`make audit` (`uv audit --locked --preview-features audit-command`) failed**, not because of a finding, but because outbound access to `api.osv.dev` is blocked by this session's network policy (gateway returned `403` to the `CONNECT`; a direct `WebFetch` to `osv.dev` failed DNS resolution entirely — both confirmed live during this run). **This is an environment limitation, not a "clean" result — do not read it as such.** Re-run `make audit` manually once network access to `api.osv.dev` is available, or from a CI runner (CI's `check` job already runs the same command on every PR/push).
- As a substitute, GitHub's Security Advisory Database (`github.com/advisories` and `github.com/lepture/authlib/security/advisories`, read via `WebFetch`) was checked by hand for the packages that moved during the `uv lock --upgrade` dry run (see below). This turned up one confirmed, currently-live issue:
  - **`authlib` 1.8.0 (currently locked, transitive via `fastmcp` → `fastmcp-slim`): CVE-2026-96760 / GHSA-6v38-4h7w-rj9h, Critical, CVSS 9.1 — JWS/JWT signature verification bypass. Affects `<=1.8.0`, fixed in `1.9.0`.** `uv lock --upgrade` moves it to `1.9.2`. The project doesn't call Authlib's OAuth/JWT verification APIs directly (auth here is the custom `BearerTokenMiddleware`), so the exploitable surface through *this* app is unclear — but `authlib` ships as part of `fastmcp`'s MCP auth stack mounted at `/mcp`, Trivy's library scan in CI will likely start flagging it once its DB catches up, and leaving a 9.1 unpatched in the lockfile is not defensible regardless of current reachability.
  - No advisory was found for `cryptography` (currently `50.0.1`, `uv lock --upgrade` moves it to `50.0.2`) in the GitHub Advisory search performed — labeled **(unverified)** only in the sense that `osv.dev`/`uv audit` itself couldn't be queried; treat the full dependency tree as unaudited this week, not as clear.
- No other advisories were found for the other packages that moved during the upgrade dry run, within the limits of the GitHub Advisory Database search performed (not a substitute for a real `uv audit`/Trivy run).

## New community practices

- **This repo already follows FastMCP's documented FastAPI-mounting pattern** — `mcp.http_app(transport="http", path="/")` mounted via `app.mount("/mcp", mcp_app)` with the MCP lifespan driven from the FastAPI lifespan, matching current guidance from `gofastmcp.com`'s own FastAPI integration docs. (verified) — [FastMCP FastAPI integration docs](https://gofastmcp.com/v2/integrations/fastapi)
- **Stateless HTTP for horizontal scaling (`stateless_http=True`)** is available in FastMCP for deployments that need to run multiple replicas without sticky sessions; this repo runs a single container today, so it's a forward-looking note rather than a current gap. (verified, applicability unconfirmed) — [FastMCP FastAPI integration docs](https://gofastmcp.com/v2/integrations/fastapi)
- **Avoid application-wide CORS middleware when mounting an OAuth-protected FastMCP server** is current FastMCP guidance; doesn't apply today since this app has no CORS middleware and doesn't use FastMCP's own OAuth providers. (verified, not applicable) — [FastMCP FastAPI integration docs](https://gofastmcp.com/v2/integrations/fastapi)
- **uv's `--require-hashes` enforcement in constraints files tightened in 0.13.0** (installs can now fail if a requirement is missing a hash) — this repo doesn't use constraints files, so no action, but worth knowing before adopting one. (verified) — [uv 0.13.0 release notes](https://github.com/astral-sh/uv/releases)
- Community blog guidance on FastAPI/Pydantic v2/uv project layout (schema/model separation, `uv add "fastapi[standard]"`, Docker layer caching with `uv sync --frozen --no-dev`) largely restates what this repo already does; no actionable gap found. **(unverified** as authoritative — these were blog posts, not official docs, per the search performed) — see Sources.

1. **Run `uv lock --upgrade` (or `uv lock --upgrade-package authlib`) and commit the updated `uv.lock` as its own PR, separately from this report.** Fixes the Critical `authlib` CVE-2026-96760 and is the only item in this report that shouldn't wait for a routine dependency cycle. *(This report is advisory only — it does not modify `uv.lock` itself, per the task's own scope limit.)*
2. **Re-run `make audit` manually (or wait for the next CI run) once network egress to `api.osv.dev` is available**, and don't treat this week's missing audit output as a clean bill of health. *Why it applies here*: the sandboxed environment that generates this report cannot reach the audit backend, but CI's `check` job runs the identical command on every push/PR, so the real gate is still intact — this report's Security section is a gap in the report's visibility, not in CI's.
3. **Bump `fastapi`, `starlette`, `fastmcp`, `uvicorn`, `pydantic-settings`, and `certifi` together** via the same `uv lock --upgrade`, then run `make check && make cov && make smoke` per the verification ritual in `reference.md`. *Why*: none carry breaking changes that touch this repo's actual code (single `Query(str)` endpoint, no Form models, no reverse-proxy `FORWARDED_ALLOW_IPS` reliance), and the `starlette` bump may let the existing `anyio.abc.BlockingPortal` `filterwarnings` ignore in `pyproject.toml` be deleted — worth checking after the bump.
4. **Bump the three uv pins (Dockerfile, `uv-pre-commit` rev, CI `setup-uv` version input) from `0.12.10` to `0.13.6` together**, plus `ruff`/`ruff-pre-commit` to `0.17.3` together. *Why*: `CLAUDE.md`/the repo's own comments already call for these three uv pins to move in lock-step, and no breaking change in the 0.13.x range touches `uv sync --locked`/`uv lock`/`uv audit`.
5. **Bump `actions/checkout` to v7 and `astral-sh/setup-uv` to v10** in `ci.yml`. *Why*: both majors' behavior changes are scoped to trigger types (`pull_request_target`, `workflow_run`, `release`) this workflow doesn't use (it only runs on `push`/`pull_request`), so the jump is safe despite being two majors for `setup-uv`.
6. **Consider mypy `2.4.1`** (bumping the `pyproject.toml` pin and the `mirrors-mypy` pre-commit rev together, per the standing lock-step policy) once `make check` passes locally — no changelog content could be retrieved to characterize the 2.3.1→2.4.1 diff (label: unverified), so verify by running the type checker rather than trusting this report.
7. No change recommended to `ruff.toml`'s rule selection, the `mypy`-pinning policy, `uv sync --locked`, or `uvx` avoidance — all remain correctly justified per the standing decisions in `reference.md`, and nothing found this week changes that basis.
