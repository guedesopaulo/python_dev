  `error sending request for url (https://api.osv.dev/v1/querybatch) ... tunnel error: unsuccessful`.
  This session's egress proxy rejects the `api.osv.dev` CONNECT — a sandbox network-policy limit, not
  a repo problem. **This is a genuine gap**: nobody has confirmed the lockfile against OSV this cycle.
  Re-run `make audit` from an unrestricted environment (or CI, which already gates on it) before acting
  on anything below as if it were a clean bill of health.
- As a manual substitute, the GitHub Advisory Database was queried for the four direct/near-direct
  packages most exposed here (`fastapi`, `starlette`, `uvicorn`, `fastmcp`):
  - `fastapi`: no advisories found for the core package. (verified)
  - `uvicorn`: no advisories found for the core package. (verified)
  - `starlette`: [CVE-2026-54283](https://github.com/advisories/GHSA-82w8-qh3p-5jfq) (High, CVSS 7.5)
    — `request.form()` silently ignores `max_fields`/`max_part_size` for
    `application/x-www-form-urlencoded` bodies, enabling event-loop-blocking / memory-exhaustion DoS.
    Affects 0.4.1 up to (not including) 1.3.1; **fixed in 1.3.1**. The lockfile already has 1.6.0, so
    this repo is not exposed — noted for completeness, not as a finding. (verified)
  - `fastmcp`: several advisories exist for the project (OAuth proxy token reuse, SSRF/path traversal
    in the OpenAPI provider, etc.), all in ranges below what's already locked here (4.0.3) or in
    optional integrations this repo doesn't use (Cursor/Gemini CLI installers). None apply to the
    locked version. (verified)
- This is not a substitute for `uv audit`: it only covers the four packages checked and does not
  cross transitives the way `uv audit` does (see reference.md's known failure mode #1 — this is
  exactly the `cryptography`-via-`fastmcp` scenario it warns about, just not something this session
  could rule out).

## New community practices

- **`uv lock --upgrade` + `git diff --stat` as a lockfile-review habit**: reviewing the diff after any
  `add`/`remove`/`upgrade` (not just the direct package you touched) is now a commonly cited uv
  workflow step, since one direct change can move several transitives. This repo's own `make cov` /
  `make check` gate already catches behavioral breakage from that, so no process change needed — noted
  as validation that the audit routine's step 2b (this same diff-and-revert) is the right shape.
  (verified) — [pydevtools: dependency groups in uv](https://pydevtools.com/handbook/explanation/understanding-dependency-groups-in-uv/)
- **Starlette's new `scope["route"]`** (shipped in the 1.7.0 this repo could adopt) lets middleware or
  exception handlers read the matched route without re-resolving it — could simplify future
  route-aware logging in `exception_handlers.py` if that's ever needed, but nothing in the current
  codebase would use it today. (verified, from the 1.7.0 release notes)
- **FastMCP + FastAPI mounting guidance**: FastMCP's own integration doc notes that when a FastAPI app
  already owns CORS/lifespan, don't double it up on the mounted MCP sub-app — this repo already follows
  that shape (single `BearerTokenMiddleware` at the FastAPI level, lifespan driven from FastAPI per
  `src/main.py`), so no change indicated. (verified) —
  [FastAPI 🤝 FastMCP](https://gofastmcp.com/integrations/fastapi)

   same-minor, no-breaking-change range per the release notes.
3. **Bump `starlette` to 1.7.0 and `uvicorn` to 0.54.0** alongside it — both are already implied by

   uvicorn), and bumping them together avoids a second lockfile churn next week.

   free by `uv lock --upgrade`.
