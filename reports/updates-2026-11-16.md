## Security

`make audit` (`uv audit --locked --preview-features audit-command`) failed locally:

```
error: Request failed after 3 retries
  Caused by: error sending request for url (https://api.osv.dev/v1/querybatch)
  Caused by: client error (Connect)
  Caused by: tunnel error: unsuccessful
```

The proxy status endpoint confirms this is a policy denial, not a transient failure:
`api.osv.dev:443` returns `403` at the agent-proxy gateway and is not in the proxy's
allowed-host list. CI runs the same command unaffected (`ci.yml`, "Audit dependencies" step),
so the lockfile is still gated on every push/PR — just not verifiable from this sandbox.

*security* updates active. Seven `dependabot/uv/*` PRs are nonetheless open against `main` right

## New community practices

- **Pin FastMCP tool names with explicit `operation_id`, not FastAPI's auto-generated ones.**
  `src/endpoints/echo.py`'s `@router.get("")` has no `operation_id`, so FastAPI derives one
  automatically and that becomes the MCP tool name via `FastMCP.from_fastapi`. Community and
  FastMCP-adjacent guidance (FastAPI-MCP docs) call out auto-generated operation IDs as a
  recurring source of cryptic tool names for LLM clients — setting it explicitly is a one-line
  fix when the next real endpoint is added. (verified pattern, unverified as an official FastMCP
  recommendation — source: [Speakeasy FastAPI+MCP guide](https://www.speakeasy.com/mcp/framework-guides/building-fastapi-server))
- **Exclude non-business routes from the generated MCP surface with `RouteMap`.** `GET /health`
  is mounted on the same FastAPI app and, since `FastMCP.from_fastapi` reflects all routes, it
  currently becomes an MCP tool too (confirmed by reading `src/main.py` — no `route_maps` passed
  to `FastMCP.from_fastapi`). FastMCP's own docs recommend `RouteMap(..., mcp_type=MCPType.EXCLUDE)`
  for routes like health checks that add no value as a tool call. (verified — source:
  [FastMCP OpenAPI/route-map docs](https://gofastmcp.com/servers/openapi))
- **Streamable HTTP over SSE is now the default expectation**, not just an option — this repo
  already does this (`mcp.http_app(transport="http", ...)`), so no change needed; noted only
  because it confirms the current setup matches current practice. (verified — MCP spec deprecated
  HTTP+SSE transport; source: [MCP streamable HTTP migration notes](https://startdebugging.net/2026/07/migrate-an-mcp-server-from-sse-to-streamable-http/))
- **`uv`'s standard `[dependency-groups]` table (PEP 735) over the legacy `[tool.uv.dev-dependencies]`.**
  This repo already uses `[dependency-groups]` in `pyproject.toml` — no change needed, confirming
  current practice. (verified by reading `pyproject.toml`; source:
  [uv dependency groups guide](https://pydevtools.com/handbook/how-to/how-to-maintain-a-uv-project/))
